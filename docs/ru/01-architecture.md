# Архитектура

## Общая картина

```
Камеры (RTSP)  ─┐
                ├─→  Frigate NVR  ─── MQTT ───→  Home Assistant  ──→  Telegram
mmWave-сенсор  ─┘      (GPU)                        (VM)          └─→  Push в приложение
   (ESPHome)             │                            ↑
                         └── кадры ──→ Ollama ────────┘
                                    (отдельный GPU)
```

Три машины, у каждой своя роль:

| Узел | Что делает | Почему отдельно |
|---|---|---|
| **Хост NVR** | Frigate: декодирование потоков, детекция, лица, запись | Нужен GPU и постоянный аптайм |
| **VM с HA** | Правила, автоматизации, MQTT-брокер, уведомления | Home Assistant OS не ставится рядом с чем-то ещё |
| **ПК с GPU** | Ollama с vision-моделью | Тяжёлые модели нельзя вешать на тот же GPU, что и детекцию |

## Поток события

Так выглядит путь «человек прошёл калитку → телефон зазвонил»:

```
1.  Камера отдаёт RTSP-поток
2.  Frigate декодирует (аппаратно, через GPU) и прогоняет кадр через YOLOv9
3.  Найден объект `person` с score выше порога
4.  Проверяется, попадает ли bounding box в зону `Exit`
5.  Параллельно: если лицо достаточно крупное и чёткое — распознавание
6.  Frigate публикует событие в MQTT: топик `frigate/events`
7.  Home Assistant ловит событие, проверяет условия:
       label == 'person'
       зона содержит 'exit'   ← в нижнем регистре, см. ниже
       камера == нужная
8.  Действия: сообщение в Telegram (несколько chat_id) + push с
    channel: alarm_stream_max — полноэкранный алерт мимо беззвучного режима
```

**Ловушка с регистром.** В конфиге Frigate зона называется `Exit`. В
шаблоне Home Assistant сравнение регистрозависимое. Если не привести
через `map('lower')`, триггер не сработает — молча, без ошибки в логах.
Это стоило нескольких часов диагностики.

## Разделение потоков detect / record

У дворовой камеры два входа с одного и того же URL, но с разными ролями:

```yaml
inputs:
  - path: rtsp://.../av_stream
    roles: [detect]
  - path: rtsp://.../av_stream
    roles: [record]
```

Причина: детекции нужен низкий latency и она готова терять качество;
записи нужен полный битрейт и она терпит задержку. На одном потоке эти
требования конфликтуют — либо детекция отстаёт, либо запись рвётся.

## Кто на какой вопрос отвечает

Это главное архитектурное решение проекта. Каждый вопрос обрабатывает
самый дешёвый компонент, который способен на него ответить:

| Вопрос | Компонент | Задержка | Почему не иначе |
|---|---|---|---|
| Есть ли человек в кадре? | YOLOv9 (ONNX, GPU) | ~30–80 мс | базовая операция |
| Кто это? | Frigate face recognition | ~100 мс | LLM решает эту задачу в 30 раз медленнее и хуже |
| В какой он комнате? | статичная карта `камера → зона` | 0 | комната не меняется, это константа конфига |
| Он упал? | mmWave-сенсор / pose estimation | < 1 с | **LLM сюда не годится:** 1–3 с на кадр |
| Что он делает? | vision-LLM (Qwen3-VL) | 10–30 с | нечем больше |
| Обычно ли это для него? | частотная статистика (SQLite) | — | это арифметика, не рассуждение |

Соблазн отдать всё одной большой модели существует, и он ошибочный:
она будет медленнее, дороже и менее предсказуема в каждой из этих ролей
по отдельности.

## Vision-LLM: окно вместо кадра

Ollama не принимает видеофайл. Схема такая:

```
клип  →  ffmpeg нарезает N равномерных кадров  →  пачка в поле `images`
      →  модель читает как последовательность во времени  →  одна строка описания
```

Расчётный бюджет: ~5 с на кадр, 5 кадров в пачке ⇒ окно ~25 с. Это не
реакция на событие, это **запись в дневник**: «встал, дошёл до кухни,
вернулся». Отсюда и название страницы «Журнал» на сайте.

Промпт жёстко ограничен: описывать только то, что видно, не угадывать
направление и намерение. Модель, которой позволено додумывать, начинает
писать «пошёл на кухню» там, где человек просто вышел из кадра.

## Приватные зоны без камеры

Спальня закрывается mmWave-сенсором 60 ГГц (Seeed MR60FDA2, ESPHome из
коробки, покрытие 3×3×3 м). Он видит присутствие, положение и падение,
но не даёт изображения. Для комнаты, где камера неуместна, это
единственный приемлемый вариант.

## Удалённый доступ

Cloudflare Tunnel, постоянный домен, поддомены под каждый сервис.
Портов на роутере не проброшено — туннель устанавливает исходящее
соединение изнутри. `trusted_proxies` в Home Assistant прописан на IP
хоста, иначе HA видит все запросы как приходящие от прокси и ломает
аутентификацию.

Наружу доступен **интерфейс**, не видеопоток.

## Устойчивость

Домашняя система без администратора. Что уже понадобилось:

- **health-check в cron** (каждые 5 минут): проверяет доступность HA и
  Frigate, перезапускает VM через `VBoxManage` и контейнер через
  `docker compose restart`. Запускается от обычного пользователя, не от
  root — VM принадлежит пользователю.
- **Отключение EEE на сетевой карте** (`ethtool --set-eee ... off` +
  systemd-юнит): чинило периодические обрывы сети.
- **Блокировка сна** (`systemctl mask sleep.target suspend.target ...`):
  ноутбук-хост с закрытой крышкой не должен уходить в сон.
- **Известная проблема без решения:** хост изредка полностью
  выключается — не спит, а именно power off. Баг задокументирован на
  Launchpad, похоже на связку ASUS BIOS/EC + ядро Linux. Программно не
  решён. Это одна из причин переезда на Raspberry Pi 5.

## Куда это движется

Текущий хост — ноутбук, что для системы жизнеобеспечения плохо. План:
Raspberry Pi 5 + AI HAT+ (Hailo-8, 26 TOPS) как основной NVR, GPU-машина
остаётся только под тяжёлые модели. Обоснование выбора железа —
[02-hardware.md](02-hardware.md).
